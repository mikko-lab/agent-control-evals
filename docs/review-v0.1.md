# v0.1 review candidate: self-review, deviations, open risks

This document records the pre-PR self-review required by the work order (section 38), the deviations from the work order, and the open risks. It contains **no hand-copied result numbers**. Results live only in generated reports: `reports/v0.1/*/report.json` and the `summary.md` rendered from it.

## Self-review (work order section 38)

| Question | Finding | Action |
|---|---|---|
| **Oracle leakage.** Can expected values come from the SUT or the adapter? | The oracle imports only `src/spec`, `src/corpus/types` and its own module. A static transitive import check fails on any path to adapter, SUT, eval, mutation or report code, on `node:fs`, and on dynamic `require`/`import` (tested by injection). Expectations are written into the corpus before any SUT call. The runner re-derives them from the scenario and refuses to run on any difference. They are never sent to the adapter (enforced by schema and test). | **Residual:** the declared policy parameters were written by reading the pinned SUT's documented demo configuration. This is a declared, shared-blind-spot risk, stated in every report. The adapter also *configures* the SUT with the declared skew windows (equal to the SUT defaults), so SUT defaults are not evaluated separately. |
| **Boundary confusion.** Is component evidence presented as runtime evidence? | Families, metrics, mutation blocks and bounds are split by boundary in code, report schema and summary. Component mutants are additionally run against every runtime case: a component mutant that changes any runtime outcome is marked invalid. | No change needed. |
| **Reason overfitting.** Is a safe runtime rejected because another fail-closed control fired first? | Runtime approval-binding cases accept `PENDING_ACTION_NOT_FOUND` / `INVALID_SIGNATURE` / the binding class. Multi-violation cases accept every violated control. A reason outside the set is a `reason_mismatch` only and never a kill or a bypass. | **Found during development:** the verifier oracle did not accept the tampered field's mismatch class, while the runtime oracle did. The corpus validity check caught it and the rule was unified (`tamperReasonsFor`). |
| **Mutation reachability.** | Static check: each patch touches one file inside the declared function at the pinned SHA, runtime paths start at a public `GuardedExecutor` API, and component mutants carry a written runtime-unreachability argument. Dynamic check: runtime mutants are killed by runtime witnesses, and component mutants change no runtime outcome. | The M15/M16 unreachability argument (pending key `${session}:${request}` over schema-validated UUIDs) was checked by hand and is documented. |
| **Mutation validity.** Does each patch break exactly one documented invariant? | Each patch removes or reorders one check. M14 moves `pendingActions.delete(key)` past the awaited execution path, which is the real "consume before first async boundary" invariant, not an invented lock. Kills require the baseline to have blocked the witness *through the mutated control* (`exposed_reason_classes`). | No change needed. |
| **Adapter masking.** Can an exception become DENY? | Unclassifiable SUT exceptions raise `AdapterError`. **Found during review:** a `CorrelationError` or `ReplayGuardError` from `resolveApproval` was interpreted as "executed, then failed" without checking that the tool ran, so a mutant could earn a kill from a random exception of that class. | **Fixed:** a per-step consistency check now requires the number of ALLOW/EXECUTE observations to equal the tool executions observed through the doubles, or the case becomes an adapter error. Tested with a fake executor. |
| **Tool test doubles.** Can state leak between cases? | Snapshot and verified restore, deep-copied outputs, per-case instances, strictly sequential adapter, and refusal of interleaved installs (a concurrent install could otherwise restore a foreign snapshot). | Tested with a fake registry and against the real SUT registry. |
| **Metrics gaming.** Can an easy family hide a hard one? | Equal allocation per family (±1) and per variant (±1). Metrics, bounds and mutation results are reported per family and variant. A family macro-average is reported, with no weighted aggregate score. **Found:** `duplicate_executions` counted the legitimate second execution after `clearSession`. | **Fixed:** duplicates now count only executions beyond the oracle's expectation. |
| **Determinism.** Could wall clock, UUID randomness, file order or the environment affect corpus bytes? | The SHA-256 counter PRNG uses integer math only. Offsets are relative, there are no absolute times, and UUIDs are SHA-256-derived. The generation order is fixed. The corpus is tested under different `TZ` and `LANG`, and CI generates it twice and compares with `cmp`. Baseline observations are hashed across two runs (`--check-observation-determinism`). | Ed25519 keys are random per adapter process. Signatures never enter observations or reports. |
| **Claims.** Could a reader take a synthetic-corpus bound as a production failure rate? | The disclaimer is a schema `const` in the report and is rendered verbatim in the summary and README. "Zero failures" is defined. The oracle limitation is a schema `const`. | No change needed. |

## Deviations from the work order

1. **The repository could not be created from this session.** The GitHub integration answered `403 Resource not accessible by integration`. The harness was built and committed locally on the feature branch and is pushed once `mikko-lab/agent-control-evals` exists.
2. **The mutation set has 17 mutants instead of about 10–16.** There are 14 runtime mutants (one per item listed in section 23: 5 capability, 5 approval, 2 replay/freshness, 1 result gating, 1 concurrency) and 3 component mutants. Nothing was added beyond the listed invariants.
3. **There is no separate linter.** `tsc --strict` is the lint gate ("lint tarvittaessa").
4. **CI has not yet run on GitHub** because the repository does not exist. Node 22 (full pipeline) and Node 24.21 (build plus the whole test suite including SUT integration tests, and the golden corpus) were verified locally only.
5. **The full 10k benchmark was run locally, not in CI.** Its report is committed under `reports/v0.1/full/` with `sut_commit`, `harness_commit` and `corpus_sha256`. The `full-benchmark` workflow is manual (`workflow_dispatch`) and has not run yet. Both committed reports (`smoke/` and `full/`) were produced with harness commit `92452ad` on a clean worktree, under Node 22. The later commits only add the read-only mirror `pushurl` hardening plus its test, documentation and the reports themselves. They do not change the generator, oracle, adapter, comparator, metrics or mutation set, and the corpus SHAs are unchanged.
6. **The SUT is configured with explicit parameters.** The adapter passes the declared request skew window (300 000 ms) and approval future skew (30 000 ms) to the SUT constructors. These equal the SUT defaults, but the defaults themselves are not exercised.
7. **SUT dependencies are installed without scripts.** The SUT's `npm ci` runs with `--ignore-scripts`; the pinned ACS has no install scripts it needs.
8. **Reason taxonomy additions.** Besides the classes listed in section 11, the taxonomy has classes the pinned SUT really emits (`CAPABILITY_MISSING`, `CAPABILITY_INVALID_SIGNATURE`, `CAPABILITY_MALFORMED`, `CAPABILITY_UNSUPPORTED_SCOPE`, `REQUEST_SIGNATURE_INVALID`, `POLICY_*`, `HUMAN_REJECTED`, `APPROVAL_GRANTED`, `PERMIT_*`, `CORRELATION_FAILURE`, `RESULT_PATH_REJECTED`). `CROSS_SESSION_MISMATCH` is reserved but not emitted, because ACS has no such code.

## Open risks

- **Shared blind spots.** The human-authored policy parameters and oracle rules mirror the SUT's documented behaviour. Faults in behaviour that both "agree" on would go undetected. Examples are a top-level-only `classification` rule, and a replay record that happens before capability verification.
- **Adapter coupling.** The ACS adapter classifies some rejections by exact error messages and audit metadata of the pinned SHA. A different SUT commit would need adapter review. That is intended by pinning, but it is a maintenance cost.
- **Mutation set coverage.** It covers the work order's listed invariants only. Faults such as a signature-verification bypass, a correlation bypass or a wildcard-scope acceptance are not in the set, and no claim is made about them.
- **Witness selection** depends on the author-declared `exposed_reason_classes` per mutant.
- **Concurrency** covers single-process promise interleavings only.
- **Clock model.** The case clock is frozen, while the SUT stamps result requests with the wall clock. Positive scenarios stay at or below a 240 s advance, which leaves an edge (elapsed equal to the ASK timeout with successful execution) unexercised.
- **Small label space.** Most scenarios use 1–2 sessions and a few requests. The corpus is broad across controls, not across scale.
- **Statistics.** Per-variant bounds rest on small n (especially in smoke) and are wide by construction. Bounds are conditional on the synthetic sampling model only.

## Readiness

The harness itself is ready for an independent v0.1 review from a design and evidence standpoint: every acceptance criterion has a mechanism and a test. It should be treated as a *review candidate* only after CI has run green on Node 22 and 24 on GitHub, which has not yet been possible. Green tests alone do not make it done: reviewers should re-check the oracle rules in `docs/evaluation-spec.md` against their own reading of the ACS spec, because that is where shared blind spots would live.
